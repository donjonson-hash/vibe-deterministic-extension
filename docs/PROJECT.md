# Vibe Deterministic Coder

**Суть:** браузерное расширение для вайбкодинга, в котором LLM только *предлагает*
патч, а детерминированное локальное ядро проверяет его, показывает смысловой дифф
и применяет целиком или не применяет вовсе, с Undo/Redo и выгрузкой без потерь.
**Пользователь:** вайбкодеры, которые меняют код через LLM и хотят видеть и
контролировать каждое изменение. Точный сегмент и число пользователей: _уточнить_.
**Стадия:** прототип. Сейчас это VS Code-расширение v0.1.0 (2 дня разработки, один
автор, нигде не опубликовано). Целевая платформа — Chrome Web Store.
**Цель сейчас:** Chrome MV3 MVP в концепции семейства
[deterministic-extensions](https://github.com/donjonson-hash/deterministic-extensions),
готовый к beta-публикации в Chrome Web Store (сначала Unlisted, как у Code Compare Local).
**Ключевые метрики:** _уточнить_. Кандидаты: доля принятых патчей без ручной
правки, доля патчей, отклонённых проверками, установки и retention за 7 дней.
**Ограничения:** дедлайн, бюджет и состав команды _уточнить_. Требование к LLM:
широкий выбор провайдеров, обязательно Anthropic; локальные модели; свой ключ (BYOK).

Правила семейства, которые прямо касаются этого проекта
(`deterministic-extensions/DETERMINISM.md`, `docs/ADOPTION.md`):
- LLM — отдельный адаптер; повторяемость его ответов **нельзя** объявлять свойством ядра.
- Базовые операции работают без LLM, ключа и сети.
- Шаблон не выполняет загруженный пользователем код «для проверки».
- Команда проверяется целиком до изменения состояния; устаревшие и повторные
  команды отклоняются; асинхронные ответы проверяются по ревизии и контексту.

## Архитектура кратко

**Сейчас (ветка `main`, VS Code):** TypeScript, единственная runtime-зависимость
`typescript` (Compiler API). Конвейер: `CommandCenter` (интент) →
`ContextManager` (AST-метаданные) → `DeterministicLLMClient` (OpenAI, JSON mode,
кеш в памяти) → `AstValidator` → `LinterRunner` → `SandboxRunner` (`node:vm`) →
`AutoFixLoop` (до 3 попыток) → `TimeMachine` (снапшоты в памяти) →
`SemanticDiffEngine`. Хранилища нет, внешний сервис один — OpenAI-совместимый
endpoint. PR #1 смержен: VS Code-версия рабочая, тесты 40/40; это финальное состояние прототипа.

**Целевая (Chrome MV3):** [ADR-0001](decisions/0001-chrome-mv3-llm-adapters.md), статус Accepted.
Объём MVP и этапы: [ROADMAP.md](ROADMAP.md).

## Риски и техдолг

1. **Платформа не совпадает с целью.** Код написан под VS Code и Node
   (`vscode`, `node:vm`, `worker_threads`, `crypto`, `process.env`). В Chrome ничего
   из этого нет: нужен перенос, а не доработка.
2. **Исполнение кода от LLM.** До PR #1 песочница `node:vm` пропускала
   `constructor.constructor("return process")()`, то есть RCE в extension host.
   PR #1 этот вектор закрыл, но концепция семейства вообще запрещает исполнять
   код для проверки. В Chrome-версии песочницы быть не должно.
3. **Обещание детерминизма LLM.** `temperature=0` и `seed` не гарантируют
   одинаковый ответ. README и позиционирование должны говорить о
   детерминированной *проверке и применении*, а не генерации.
4. **Код пользователя уходит третьей стороне.** С BYOK код отправляется выбранному
   провайдеру. Это нужно раскрыть в privacy policy и в карточке CWS, получить
   явное согласие и запрашивать host permission на каждый endpoint во время работы.
   Это отличает продукт от остального семейства (там `connect-src 'none'`).
5. **Нет проверки в реальной среде.** Нет eslint, нет теста в настоящем редакторе или браузере. Голосовой ввод заявлен
   в README, но не реализован.
